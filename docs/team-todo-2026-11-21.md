## Part 1 — What we agreed today

### The goal (from the board)
1. Take an invoice and extract its information.
2. Read and code invoices (GL account + department), with a human confirming.
3. Pay invoices from the same platform (alongside Brim card).
4. Keep an audit trail of every action.

### The roles (from the board)
| Role | What they do |
| --- | --- |
| Employee | Submits invoices / requests |
| AP Clerk | Processes invoice data |
| Approver (dept manager) | Approves the data and the invoice |
| Finance Manager | Approves above department limits, sees department spending, delegates when away |
| Controller | Manages users, roles and AP; releases payments |
| Auditor | Reads everything, traces actions, exports |

### Understandings from the walkthrough
These came up while testing the build. Each is already how the app behaves unless it says otherwise.

- **The LLM only reads documents.** Coding suggestions come from history ("7 of 8 past lines went to 5010"), not AI.
  Tax codes come from what's printed on the invoice and are checked against the delivery province (rule T01).
  The human always confirms. If anyone pitches an "AI bot" for coding, the honest answer is: deterministic and explainable, on purpose.
- **What a PO is:** Harborline's own advance approval to spend (vendor, amount, department, who asked, who approved).
  The vendor quotes its number on the invoice. Only some vendor categories require one (`requires_po`).
  In this batch, all 8 invoices with a PO field have it **blank**. 6 have an open PO for the same vendor the clerk could
  link; Torque's PO-2026-0037 is partially invoiced, so check its remaining balance; Brightline has none and needs a
  Finance Manager override.
- **Missing required PO (P13) is a BLOCK flag:** the clerk can't submit until a PO is linked (flag clears itself) or a
  Finance Manager / Controller overrides it with a written reason.
- **"CFO" is not a separate role.** Priya is a Controller/Admin; "cfo" is only an approval step in rule P04, filled by
  the Controller/Admin with no manager.
- **Who releases payments:** up to $100k → Finance Manager or Controller/Admin; over $100k → Controller/Admin only;
  never anyone who approved the invoice (D-077). The dataset's P09 names only the FM; we follow the PRD.
- **Over $250k the CFO may release what she approved**, as a logged separation-of-duties exception (D-091, team
  decision; replaces D-078). Everyone else who approved is still refused. Not reachable with this data (largest invoice $28,377).
- **Unverified bank details (B01/B02) hold the payment, not the approval** (D-079). Approving moves no money; release
  checks the bank account was verified by callback.
- **The audit trail persists** in Postgres and a database trigger blocks edits. Only the demo reset wipes it, and it
  then writes `DEMO_RESET` as event 1.
- **Resetting on Windows:** `powershell -ExecutionPolicy Bypass -File .\scripts\reset-and-seed.ps1`, then
  **Process inbox** as Jordan, because reset doesn't re-run the incoming batch.
- **The email inbox is simulated** from `dataset_given/inbox/emails.json` (59 emails). We don't connect to a real mailbox.

## Part 2 — Ground rules for the new work
These keep the app consistent with what's already built. Break one only with a decision entry.

1. **Every invoice state change goes through `InvoiceWorkflowService`**, which checks permission and writes the audit row in the same transaction.
2. **Nothing is ever hard-deleted.** "Delete" and "undo" are new actions that are themselves audited; the original record and its history stay.
3. **Roles are enforced on the server** (`@PreAuthorize` + checks in the service). Hiding a button is only cosmetic.
4. **Money is `BigDecimal`** and travels as a string in JSON.
5. Regenerate frontend types after backend changes: `npm run gen:api` (backend running).
6. **Shared file warning:** T1 (withdraw duplicates) and T2 (undo) both change `InvoiceStateMachine.java`. Whoever lands second rebases.

## Part 3 — Tasks

Sizes: **S** < 1 h · **M** 1–2 h · **L** 2–4 h. Tasks are independent unless noted.

### T1 — Employees can withdraw an invoice flagged as a duplicate — M
**Owner:** ______  
**Why:** an employee who uploads the same bill twice should be able to clean up their own mistake.  
**Decision:** "delete" = **withdraw**, a soft delete. The bill moves to a new terminal status `WITHDRAWN`; the
document, flags and audit history stay; it disappears from default lists (filter to show it).  
**Rules:**
- Allowed only when the invoice is `DUPLICATE` (or has an open D01/D03 flag) **and** has no payment.
- Who: the employee who uploaded it (their own only), the AP clerk, Admin. Approvers and Auditor can't.
- A reason is required and written to the audit log (`INVOICE_WITHDRAWN`).

**Where:** `InvoiceStateMachine` (add `DUPLICATE → WITHDRAWN`), `InvoiceWorkflowService`, a new
`POST /invoices/{id}/withdraw` with `@PreAuthorize`, a "Withdraw" button on the invoice screen, a status filter on the
invoice list.  
**Done when:** an employee uploads a file twice → the second is `DUPLICATE` → they withdraw it → it's hidden from their
list, shows in the audit log, and another employee's bill returns 403. Unit test for the transition and the role check.

### T2 — Undo — L
**Owner:** ______  
**Why:** people click the wrong thing. They need a safe way back.  
**Decision:** undo is a **compensating action**, never an edit of history. It writes its own audit row ("UNDO of
event #123") and only works where reversing is safe.

| Action | Undoable? | Rule |
| --- | --- | --- |
| Field correction / coding override | ✅ | Revert to the previous value (taken from the audit row's before-snapshot) while the invoice is still `IN_REVIEW` |
| Flag acknowledged / resolved | ✅ | Re-opens the flag while the invoice is `IN_REVIEW` |
| Submit for approval | ✅ | Back to `IN_REVIEW` if no approver has acted yet (transition already exists) |
| Approval (one step) | ✅ | Only by the person who approved, only if the next step hasn't acted and no payment is prepared |
| Reject | ✅ | Already supported: reopen to `IN_REVIEW` |
| Hold | ✅ | Already supported: release hold |
| Vendor approval | ⚠️ | Only if no payment to that vendor has been prepared |
| Bank change verified | ❌ | Raise a new change request instead (fraud-sensitive) |
| Payment released / batched / settled | ❌ | Money has moved. Use a payment reversal / "failed" flow instead |
| Audit log | ❌ | Never |

**Where:** a new `UndoService` that maps an audit event to its reverse action and calls the existing workflow/service
methods; `POST /audit/{eventId}/undo`; an "Undo" link on the toast after an action and on the invoice's History tab
(only for your own recent, undoable actions).  
**Done when:** each ✅ row has a test; the audit log shows both the action and its undo; undo of a ❌ action returns
400 with the reason.  
**Coordinate with:** T1 (both touch `InvoiceStateMachine`).

### T3 — Purchase orders page — M
**Owner:** ______

### T5 — Send email (simulated outbox) — M
**Owner:** ______  
**Depends on:** T4's viewer (for Reply), but compose can start independently.  
**Decision:** **no real sending.** Messages go to an `outbound_emails` table and appear in a "Sent" folder. Real SMTP
is out of scope (credentials, spam risk, demo safety).  
**Scope:** Reply / Compose with templates:
- ask a vendor for a missing PO number (from a P13 flag);
- answer a payment inquiry with the payment status (EM-057);
- tell a vendor their bill was rejected / is a duplicate.

Roles: clerk, FM, Admin. Every send is audited (`EMAIL_SENT`, recipient, subject, linked invoice).  
**Guard rail:** never offer "reply to confirm bank details". Bank changes are verified by **calling a known number**,
not by email. Put that sentence on the bank-change screen too.  
**Done when:** from a P13 flag, "Ask vendor for PO" opens a pre-filled draft → Send → shows in Sent and the audit log.
